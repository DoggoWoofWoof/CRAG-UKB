# Freebase canonical tree — 2026-09-12

What was done on 2026-09-12 to bring the Freebase layer (`freebase_v3`, `CRAG_FREEBASE_CANONICAL`,
301,977,131 nodes / 2,062,430,072 edges, frozen 2026-09-07, closed for computation 2026-09-11)
to the same normalised, frozen form as the six datasets, under the directive *"complete freebase
all nodes should have names etc"*. The served state is described by
`data/final_canonical/HANDOFF.md` §11 and pinned by `data/final_canonical/freebase/DATASET.json`;
this note is the diary. The companion note for the six is `docs/CANONICAL_FREEZE_2026-09-12.md`.

## 1. What "complete" meant, and what it did not

The six datasets are served as one tree each: nodes in position order, edges as arrays over
positions, one `DATASET.json` per tree, one freeze record over all. The Freebase layer was not:
its nodes lived in 262 hash-sharded parquet files keyed by a 64-bit uid, its edges in 264 parts
keyed by uid, its metadata by id string, and 7,221,354 nodes had no display name at all (the
"floor" left after the 2026-09 name-recovery campaign closed). "Complete" here means:

1. every one of the 301,977,131 nodes carries a display name, with its provenance kept
   distinguishable (`name_kind`, `name_source`, `name_rule`, `is_original_name`), the three
   nameless grades kept as audit columns, nothing relabelled upward;
2. the whole universe laid out as `data/final_canonical/freebase/` in the position form of the
   six, with a loader (`canonical.Freebase`), a verifier, a `DATASET.json`, and the tree pinned
   inside `CANONICAL_FREEZE.json`.

It does **not** mean embeddings: encoding 302M nodes is infeasible on this machine
(`FREEBASE_V3_CLOSURE_STATUS`: "universe encodings INFEASIBLE (CPU)"), so the tree has none and
`DATASET.json["not_included"]` says so. It has no queries either (Freebase is a KB, not a
benchmark; WebQSP is the 2,592,894-node RoG subgraph and is bridged, not merged).

## 4. Things a reader should know that no record states on its own

### 4.1 `name` is never empty, but only `name_kind` 0–2 is a label
Kinds 3–4 are the node's own identifier made readable, kind 5 a structural inference, kind 6 an
evidence-based description that embeds the MID (`"Freebase object m.0qrbx8m (MusicBrainz
recording 1430512f-…)"`, `"Document m.046zqm (Text: Reginald Denny, a white …)"`). Nothing in
kinds 5–6 may be presented as an authentic Freebase label; `is_original_name` is the one-bit
answer to "did Freebase itself assert this string for this node".

### 4.2 The placeholder and bare-MID counts are heuristics, and here is what they caught
`compose_final` flags any served name that *begins* with the word Unknown/Unnamed (7,679 rows)
or matches `^[mg]\.[0-9a-z_]+$` (18 rows). All 18 bare-MID-looking names are ORIGINAL
(`"m.jpg"`, `"m.albarn"`, `"g.parrot"` — the source asserted them). Of the 7,679 placeholder-
looking names, 4,738 are actual names (`"Unknown (deceased)"`, literal descriptions starting
"Unknown…") and 2,941 are derived names that begin that way only because the Freebase name they
are built from does (`"Unknown Pleasures — notable for Musical Release"`, `"Unknown Soldier
(Italian Wikipedia)"`, `"Unknown Hinson in The Boxmasters"`; 2,416 `common.notable_for#0`, 255
`URI_DERIVED`, 104 `MERGE_SUCCESSOR_NAME`, 166 other mediator roles). No derived name is a bare
MID and no GENERATED_FLOOR or KEY_SEMANTIC name is a placeholder; `verify_freebase` re-checks the
floor per row.

### 4.3 Direction, and why the `flag` column is all zero
`src → dst` is Freebase's own subject → object on the master side of each reverse-property pair.
V3 PASS D (`v3_pass_d.py`) swaps `src`/`dst` when it moves a reverse-side assertion to the master
side and keeps `flipped = 0` whenever any copy of the fact was asserted directly. All 126,994,565
reverse-side assertions in this source had a directly asserted master-side twin
(`duplicates_where_both_directions_were_asserted` = `edges_flipped_to_master_side`), so the
served flag is 0 on every one of the 2,062,430,072 edges — measured by the forward build and
again by the verifier, and stated as such in `DATASET.json`; earlier draft text that described
per-edge flip marks was wrong and was corrected before the freeze. The one re-oriented family is
the type declaration: `type.object.type` does not occur; types are stored as
`(type, type.type.instance, instance)`, so a node's types are the *sources* of its
`type.type.instance` in-edges (`metadata/type_{indptr,val}.npy` answers the same question without
a scan; `education.education` has 530,525 such out-edges, all to CVTs).

### 4.4 `education.education.institution` from an entity to a CVT is Freebase, not the build
About 15 % of that relation's edges run ENTITY_MID → CVT_MEDIATOR. Checked from the bucket files:
each such source is an untyped node with only a Freeq key, the target an `education.education`
CVT with a `student` edge and no `institution` edge of its own. The relation has 526,643 raw
master-side assertions and 526,643 served edges, so these are Freebase's own subject → object
assertions (a Freeq load that pointed the *institution* slot at another education record); the
generated names render them as asserted (`"… (institution: Education record for …)"`).

### 4.5 The IDIR ruling was applied, the cascade file's flag was not
`_acquisition/cascade_names.parquet` marks its 2,233 `IDIR_FREEBASE_NAME` rows
`is_original_name = false` (the file predates the ruling). `V3_ACTUAL_NAME_LAYER_FROZEN` rules
those rows to be Freebase name assertions (`HISTORICAL_FREEBASE_NAME`; the audit-oracle rule is
about structure), so `compose_names.py base` serves them as RECOVERED_ORIGINAL (287,703 =
285,433 + 2,233 + 37). The first base run had composed them as RECOVERED_EXTERNAL; it was re-run.

### 4.6 One display_text disagrees with the served name, and it is not a bug
Of 50,815,330 rows whose `overlay_v1` display_text is a current Freebase name, exactly one
(`m.011q6t0v`) is served differently: its asserted name is the single space `" "`, which
`overlay_v1` never accepted as a name, so the row resolved by the next rule (INFERRED
`RELATION_SIGNATURE_NAME`, "Notable types of Location"). Recorded with the example in
`NAMES_V4_BASE.json`; nothing was overwritten.

### 4.7 The uid rule is part of the identity
`position(id) = searchsorted(node_uid, hash(id.encode()))` under `PYTHONHASHSEED=0` (V3 PASS B's
minting rule; literals hash `lexical_form \t datatype \t language`). Every builder refuses to run
without the seed; `canonical.Freebase.position` needs it; `bridge/schema_index.parquet` and
`bridge/webqsp_positions.npy` resolve schema ids and webqsp nodes without it.

### 4.8 What was not acquired
1,531,606 floor nodes carry a decodable external identity in a key — 1.46M of them MusicBrainz
NGS ids in `dataworld.freeq` variables (`"MusicBrainz recording 1430512f-…"`). Their names could
be fetched from MusicBrainz (exact-id lookup, ≤ 1 req/s), but external acquisition needs the
owner's explicit approval before a single request is made (standing rule); nothing was fetched,
the identity is served as the name.
